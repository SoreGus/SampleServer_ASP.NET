# Checklist — Modelo de dados

## Diretrizes

O modelo assume PostgreSQL para dados relacionais e Object Storage privado para fotos, vídeos e documentos. Modelos completos de entrada e saída pertencem ao backend e ao frontend; o banco armazena apenas dados necessários para consistência, histórico e consultas.

## Herança de localização

A localização efetiva é resolvida nesta ordem:

1. Localização configurada no setor da execução.
2. Localização do primeiro setor ancestral que possuir configuração.
3. Localização da organização.
4. Ausência de restrição geográfica quando nenhuma localização estiver configurada.

Latitude, longitude e raio devem ser herdados como uma única configuração. O backend não deve combinar coordenadas de uma entidade com o raio de outra.

`ChecklistRecord` e `TaskRecord` preservam as coordenadas capturadas durante a execução. `IsInsideAllowedArea` preserva o resultado da validação realizado naquele momento, mesmo que a configuração seja alterada posteriormente.

## Regras de persistência

- Toda consulta de dados organizacionais deve ser limitada por `OrganizationId`.
- `AccessCode` identifica a organização, mas não concede papel nem permissão; o acesso deve ser aprovado conforme as regras da organização.
- `SupervisorMemberId` deve apontar para um membro da mesma organização, não pode apontar para o próprio registro e não pode formar ciclos.
- Checklists publicados e registros concluídos preservam o histórico e não são reescritos livremente.
- Quando um agendamento possuir executores específicos, o sistema gera uma execução para cada membro associado; sem executores específicos, usa setor e turno.
- Jobs de escalada devem ser idempotentes para não registrar ou notificar o mesmo nível mais de uma vez.
- Valores em `jsonb` devem ser validados pelo backend antes da persistência.
- Senhas, tokens e segredos nunca são armazenados em texto puro.
- Arquivos são privados e acessados por autorização ou URL temporária.
- Auditoria e logs técnicos possuem objetivos distintos.
